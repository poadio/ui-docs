Données liées (@poadio/data)

@poadio/data 0.1.1 branche les composants sur un projet poad : des stores déclarés en clair (une table, une vue, une fonction, des données locales), lus et écrits sous les droits RLS de l'utilisateur connecté, et des composants qui s'y lient par store + field. Pages, tri, filtres et recherche partent au serveur ; l'écriture garde un brouillon, valide, détecte les conflits ; le temps réel tient tout à jour. Aucune dépendance tierce, le même moteur sous les quatre rendus.

Installer

bun add @poadio/data @poadio/data-js   # ou @poadio/client-js, qui contient data-js

Les rendus (@poadio/ui-angular, ui-react, ui-vue, ui-elements) dépendent déjà de @poadio/data : c'est le même moteur partout. @poadio/data-js est une dépendance facultative — seul le transport @poadio/data/poad s'en sert.

Déclarer les stores

Un constructeur par source, rien de caché : le nom du store (celui que les composants citent), puis la table, la vue ou la fonction. load(params?) charge sans composant et garde les paramètres pour les relectures ; get(), set(), save(), revert(), refresh() font le reste.

import { store } from '@poadio/data';
import { poadTransport } from '@poadio/data/poad';

store.connect(poadTransport(poad));   // le client poad de l'utilisateur connecté (son jeton, donc son RLS)

const villes    = store.table('villes', 'villes', { reference: true, order: ['nom'] });
const chantiers = store.table('chantiers', 'chantiers', { order: ['nom'], pageSize: 20, search: ['nom'], version: 'version' });
const chantier  = store.table('chantier', 'chantiers', { key: null, version: 'version' });
const taches    = store.table('taches', 'taches', { parent: { store: 'chantier', column: 'chantier_id' } });
const charge    = store.view('charge', 'charge_responsables', { readOnly: true });
const stats     = store.pgfn('stats', 'stats_villes', { args: { statut: null } });
const filtres   = store.define('filtres', { statut: 'en_cours' });   // données locales

await chantiers.load({ where: { statut: 'en_cours' } });   // sans composant ; paramètres gardés
await chantier.load({ key: 42 });
chantier.set('nom', 'Pont neuf');   // brouillon
await chantier.save();              // false : erreurs ou conflits dans chantier.get().edit
chantier.revert();
ConstructeurSourceÉcriture
store.define(nom, données)données locales (objet → enregistrement, tableau → lignes)en mémoire
store.table(nom, table, options)table ; { key } → un enregistrementoui, sous le RLS
store.view(nom, vue, options)vue Postgressi Postgres sait la modifier ; readOnly: true l’interdit
store.pgfn(nom, fonction, { args })fonction Postgres (tableau → lignes, result: 'record')lecture seule
store.fn(nom, fonction, { args })fonction poadlecture seule

Lier les composants

Un composant reçoit un store (l'objet, ou son nom) et un field (un champ) ou des fields (les colonnes, les rôles). Le JSON data — { "store": "chantier", "field": "nom" } — fait la même chose : c'est la forme du designer et du MCP. Jamais de <select> natif : les listes de choix sont des poad-select, poad-combo, poad-multiselect…

Angular
<poad-table [store]="chantiers" [fields]="colonnes" />

<poad-field [label]="'Nom'" [store]="chantier" field="nom"><input poadInput /></poad-field>
<poad-field [label]="'Ville'" [store]="chantier" field="ville_id"><poad-select /></poad-field>

<poad-taskboard [store]="taches" [fields]="[
  { field: 'statut', type: 'enum', roles: ['status'], options: statuts },
  { field: 'rang', roles: ['order'] }, { field: 'titre', roles: ['label'] }]" />
React · Next.js
<PoadTable store={chantiers} fields={colonnes} />

<PoadField label="Nom" store={chantier} field="nom"><PoadInput /></PoadField>
<PoadField label="Ville" store={chantier} field="ville_id"><PoadSelect /></PoadField>

<PoadTaskboard store={taches} fields={[
  { field: 'statut', type: 'enum', roles: ['status'], options: statuts },
  { field: 'rang', roles: ['order'] }, { field: 'titre', roles: ['label'] }]} />
Vue · Nuxt
<PoadTable :store="chantiers" :fields="colonnes" />

<PoadField label="Nom" :store="chantier" field="nom"><PoadInput /></PoadField>

  { field: 'statut', type: 'enum', roles: ['status'], options: statuts },

<poad-table store="chantiers" fields='["nom", { "field": "budget", "format": { "currency": "EUR" } }]'></poad-table>

<poad-field label="Nom" store="chantier" field="nom"><input /></poad-field>
<poad-field label="Ville" store="chantier" field="ville_id"><poad-select></poad-select></poad-field>

<!-- ou le JSON, celui du designer et du MCP -->
<poad-taskboard data='{ "store": "taches", "fields": [
  { "field": "statut", "type": "enum", "roles": ["status"] }, { "field": "rang", "roles": ["order"] } ] }'></poad-taskboard>

Les rôles des fields

Aucun bloc propre à un composant : un field se décrit par son type et ses roles, et chaque composant y trouve ce qu'il lui faut. Un rôle inconnu est refusé.

RôlesLus par
label, description, imagetexte d’un élément, d’une option, d’un nœud
key, searchvaleur d’une option, colonnes de la recherche (au serveur)
start, end, resource, progresscalendrier, planning, gantt
status / group, ordertableau de tâches (colonne, rang), agendas
latitude + longitude, geometrycarte (emprise relue après un déplacement)
parentarbre, organigramme, table en arbre, gantt
valuegraphique (une série par field)

Références, enfants, écriture, temps réel

Store de référence

reference: true : chargé une fois, partagé par toutes les listes de choix qui le citent (options: { store: 'villes' } sur le field), gardé, tenu à jour par le temps réel.

Store enfant

parent: { store, column } : les lignes de l’enregistrement parent, enregistrées avec lui (un seul save()), annulées avec lui.

Écriture et conflits

Brouillon, validation (required, min, pattern…), refus du RLS affiché sur le champ ou la ligne. Avec version, une modification faite ailleurs entre-temps devient un conflit : « Garder la mienne » ou « Prendre la leur », jamais d’écrasement silencieux.

Temps réel

Une table de la publication poad_realtime arrive sans recharger, filtrée par le RLS de chacun ; store.get().realtime dit l’état du flux.

Le modèle JSON

Ce qu’écrivent un designer, le MCP ou un agent IA : une description de store et des liaisons, versionnées et validées strictement (validate, store.fromJSON, s.toDescription() ; schémas @poadio/data/schema/store.v1.json et binding.v1.json). Une clé inconnue est refusée, jamais ignorée.

{ "name": "chantiers", "source": "table", "table": "chantiers", "order": ["nom"], "pageSize": 20, "version": "version",
  "fields": [{ "field": "nom", "roles": ["label", "search"] },
             { "field": "ville_id", "options": { "store": "villes" } },
             { "field": "debut", "type": "date", "roles": ["start"] }, { "field": "fin", "type": "date", "roles": ["end"] }] }

{ "store": "chantier", "field": "nom" }
{ "store": "chantiers", "fields": [{ "field": "lat", "roles": ["latitude"] }, { "field": "lon", "roles": ["longitude"] }] }

Deux applications complètes
