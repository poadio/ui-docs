Stores (@poadio/data)

@poadio/data 0.2.0: stores declared in plain sight (a table, a view, a function, local data), read and written under the signed-in user's RLS, and components that bind to them with store + field. The same engine under the four renderers, with no third-party dependency.

The complete example

Everything you need, nothing hidden: the poad client, the stores connected to it, one store declared and loaded. The address and the anon key are those of the project (poad info); the anon key is public, what protects the data is RLS.

stores.ts
import { createClient } from '@poadio/client-js';
import { store } from '@poadio/data';

// 1. The poad client: the project address and its anon (public) key
const poad = createClient('https://<identifier>.poad.io', '<anon key>');

// 2. Give it to the stores: they read with the signed-in user's token, hence under their RLS
store.connect(poad);

// 3. Declare a store and load it
export const chantiers = store.table('chantiers', 'chantiers', { order: ['nom'], pageSize: 20 });
await chantiers.load();

Binding it to a component

The component takes the store and its fields (the columns). Paging, sorting, filters and search go to the server, in one request; loading, error and total come from the store.

Angular
import { Component } from '@angular/core';
import { PoadTableComponent } from '@poadio/ui-angular';
import { chantiers } from './stores';   // the file of the example above

@Component({
  selector: 'app-chantiers',
  imports: [PoadTableComponent],
  template: `<poad-table [store]="chantiers" [fields]="fields" showSearch />`,
})
export class Chantiers {
  readonly chantiers = chantiers;
  readonly fields = ['nom', 'ville', { field: 'budget', type: 'number', format: { currency: 'EUR' } }];
}
React · Next.js
'use client';   // Next.js: the table lives in the browser

  return <PoadTable store={chantiers} fields={['nom', 'ville', { field: 'budget', type: 'number', format: { currency: 'EUR' } }]} showSearch />;

Minimal example that works

The smallest complete application: a notes table and its RLS (one migration, one seed), a page that creates the client, connects the store and shows a bound <poad-table>. Web components, published npm packages only: examples/stores-minimal. You need Docker, bun and the poad CLI (npm i -g poad); bun start starts the poad project (database, migration, seed), then Vite.

git clone https://github.com/poadio/ui.git
cd ui/examples/stores-minimal
bun install
bun start

Two complete applications, “Suivi de chantiers” (sign-in and per-user RLS, server-side list, record form with its tasks, conflicts, realtime, calendar, taskboard, map), each written on the published packages: web components and Angular. Engine details: @poadio/data README.

Install

bun add @poadio/data @poadio/client-js   # or @poadio/data-js alone, without auth or storage

The renderers (@poadio/ui-angular, ui-react, ui-vue, ui-elements) already depend on @poadio/data: the same engine everywhere. @poadio/client-js (or @poadio/data-js alone) stays an optional dependency: store.connect(poad) recognises the client by its shape, without importing it. When the user changes, realtime restarts by itself under their token. poadTransport(client, options) from @poadio/data/poad is only for advanced cases (data-js alone, functions through invoke, followAuth: false).

Declaring the stores

One constructor per source, nothing hidden: the store name (the one components refer to), then the table, view or function. load(params?) loads without a component and keeps the parameters for later reads; get(), set(), save(), revert(), refresh() do the rest.

import { store } from '@poadio/data';

store.connect(poad);   // poad: the client of the complete example, above

const villes    = store.table('villes', 'villes', { reference: true, order: ['nom'] });
const chantiers = store.table('chantiers', 'chantiers', { order: ['nom'], pageSize: 20, search: ['nom'], version: 'version' });
const chantier  = store.table('chantier', 'chantiers', { key: null, version: 'version' });
const taches    = store.table('taches', 'taches', { parent: { store: 'chantier', column: 'chantier_id' } });
const charge    = store.view('charge', 'charge_responsables', { readOnly: true });
const stats     = store.pgfn('stats', 'stats_villes', { args: { statut: null } });
const filtres   = store.define('filtres', { statut: 'en_cours' });   // local data

await chantiers.load({ where: { statut: 'en_cours' } });   // without a component; parameters kept
await chantier.load({ key: 42 });
chantier.set('nom', 'Pont neuf');   // draft
await chantier.save();              // false: errors or conflicts in chantier.get().edit
chantier.revert();
ConstructorSourceWriting
store.define(name, data)local data (object → record, array → rows)in memory
store.table(name, table, options)table; { key } → one recordyes, under RLS
store.view(name, view, options)Postgres viewwhen Postgres can update it; readOnly: true forbids it
store.pgfn(name, function, { args })Postgres function (array → rows, result: 'record')read-only
store.fn(name, function, { args })poad functionread-only

A component takes a store (the object, or its name) and a field (one field) or fields (the columns, the roles). The data JSON — { "store": "chantier", "field": "nom" } — does the same: it is the form of the designer and the MCP. Field roles

No component-specific block: a field is described by its type and its roles, and each component finds what it needs there. An unknown role is refused.

RolesRead by
label, description, imagetext of an item, an option, a node
key, searchvalue of an option, search columns (server-side)
start, end, resource, progresscalendar, scheduler, gantt
status / group, ordertaskboard (column, rank), calendars
latitude + longitude, geometrymap (extent read again after a move)
parenttree, org chart, tree table, gantt
valuechart (one series per field)

References, children, writing, realtime

Reference store

reference: true: loaded once, shared by every choice list that refers to it (options: { store: 'villes' } on the field), kept, kept up to date by realtime.

Child store

parent: { store, column }: the rows of the parent record, saved with it (one save()), reverted with it.

Writing and conflicts

Draft, validation (required, min, pattern…), RLS refusal shown on the field or the row. With version, a change made elsewhere in the meantime becomes a conflict: “Keep mine” or “Take theirs”, never a silent overwrite.

Realtime

A table in the poad_realtime publication arrives without reloading, filtered by each user’s RLS; store.get().realtime tells the state of the stream.

Navigation, queries and batches

Everything is written in code AND in JSON (one description for the designer, the MCP and the code), except what is a function: events, filterBy, a computed field given as a function.

Cursor: the current record

A row store has a current record, like a TDataSet or an ExtJS store. Pages are read when needed; leaving a modified row (batch mode) saves it first, a refusal keeps the cursor on it. { store, field } on a row store is the field of the current record, both ways, on the four renderers; the bound table marks the current row and a click makes it current.

const albums = store.table('albums', 'albums', { order: ['annee'], pageSize: 20, save: 'batch' });

await albums.first();             // the first of the WHOLE result
await albums.next();              // at the end of the page, the next one is read
await albums.last();              // only the last page is read (total)
await albums.locate({ id: 7 });   // in the page, else on the server
albums.get().current;             // { index, row, bof, eof, active }

Chained query

The same JSON description, written in code. Operators: those of data-js (eq, ne, gt, gte, lt, lte, in, notIn, like, ilike, notLike, notIlike, is, not, between, notBetween, contains, containedBy, overlap, match); any other is refused (data.unknown_operator). A :name parameter gets its value when reading: the description stays static.

const albums = store.table('albums', 'albums')
  .select('titre, annee, serie(nom)')
  .where('annee', 'gte', ':depuis')          // parameter: load({ depuis: 2010 })
  .where('serie.nom', 'ilike', '%x%')
  .or((w) => w.where('note', 'gte', 4).where('coup_de_coeur', 'eq', true))
  .order('annee', 'desc').order('titre')
  .pageSize(20);

albums.toDescription();   // the same JSON as the designer; store.fromJSON(…) reads it back
await albums.load({ depuis: 2010 });
{ "name": "albums", "source": "table", "table": "albums",
  "select": ["titre", "annee"], "include": { "serie": { "select": ["nom"] } },
  "where": { "and": [{ "annee": { "gte": ":depuis" }, "serie.nom": { "ilike": "%x%" } },
                     { "or": [{ "note": { "gte": 4 } }, { "coup_de_coeur": { "eq": true } }] }] },
  "order": [["annee", "desc"], "titre"], "pageSize": 20 }

Events

on(name, fn) returns the unsubscribe; beforeload and beforesave cancel (false) or complete. Never serialised.

const off = albums.on('beforeload', ({ params }) => (params.depuis ? undefined : false));   // false: cancels
albums.on('beforesave', () => ({ modifie_par: moi.id }));   // set on every row sent
albums.on('saved', ({ ids }) => toast(ids.length));
albums.on('error', ({ error, during }) => console.warn(during, error.code));   // load | save | move
albums.on('current', ({ index, row }) => {});   // also load, change
off();

Computed fields

Displayed, sortable within the page, never sent to the database. In JSON, an expression evaluated by the engine (add, mul, round, concat, if…), never an executed string.

store.table('lignes', 'lignes', { fields: [
  { field: 'ttc', compute: (r) => r.ht * 1.2 },                                   // code only
  { field: 'ttc2', type: 'number', compute: { round: [{ mul: ['ht', 1.2] }, 2] } },  // JSON: an expression, never eval
] });

Grouping and totals

Computed by the server, under the user’s RLS: with groupBy, the rows are the groups; without, totals holds those of the whole result.

const parSerie = store.table('parSerie', 'albums').groupBy('serie_id').sum('prix').count();
// rows: the groups — [{ serie_id: 1, count: 4, sum: { prix: 59 } }, …]

const albums = store.table('albums', 'albums', { pageSize: 20 }).sum('prix').count();
albums.get().totals;   // { count: 45, sum: { prix: 1234.5 } } — the WHOLE filtered result, under RLS
// bound <poad-table>: a totals row at the foot

Local filter

On the loaded rows, without a request, combined with the server filters.

albums.filterBy((r) => r.prix > 10);   // the loaded rows, no request
albums.get().filtered;                 // true
albums.clearFilterBy();

Reload on dependency

The field of another store’s current record becomes a parameter, and the store reloads when it changes: master-detail, generalised. A record store follows its key ("param": "key"); autoLoad loads without waiting for a component.

{ "name": "auteurs", "source": "table", "table": "auteurs", "order": ["nom"] }
{ "name": "albums", "source": "table", "table": "albums", "where": { "auteur_id": ":auteur" },
  "dependsOn": { "store": "auteurs", "field": "id", "param": "auteur" } }
{ "name": "fiche", "source": "table", "table": "albums", "key": null, "autoLoad": true,
  "dependsOn": { "store": "albums", "field": "id", "param": "key" } }

Batch save

The pending changes of several stores go in ONE transaction of the data service (engine 0.38): all or nothing, each operation under RLS, each with the version it read. A refusal writes nothing and puts the error (or the conflict) on the faulty row.

commande.set('client', 'B');
lignes.set(id, 'qte', 3);
lignes.insert({ commande_id: 1, qte: 7 });

await store.sync([commande, lignes]);   // ONE batch, ONE transaction: all or nothing
await store.saveAll();                  // every store of the registry

The JSON model

What a designer, the MCP or an AI agent write: a store description and bindings, versioned and strictly validated (validate, store.fromJSON, s.toDescription(); schemas @poadio/data/schema/store.v1.json and binding.v1.json). An unknown key is refused, never ignored.

{ "name": "chantiers", "source": "table", "table": "chantiers", "order": ["nom"], "pageSize": 20, "version": "version",
  "fields": [{ "field": "nom", "roles": ["label", "search"] },
             { "field": "ville_id", "options": { "store": "villes" } },
             { "field": "debut", "type": "date", "roles": ["start"] }, { "field": "fin", "type": "date", "roles": ["end"] }] }

{ "store": "chantier", "field": "nom" }
{ "store": "chantiers", "fields": [{ "field": "lat", "roles": ["latitude"] }, { "field": "lon", "roles": ["longitude"] }] }
